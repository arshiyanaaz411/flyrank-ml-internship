Can Pre-Click Features Predict CTR for New Clients? A Grouped-Validation Audit and a Human-Review Content Playbook

Arshiya Nazneen Dukandar · November 2026

Abstract

Content teams need a way to decide which pages deserve review first, so this study asks whether features known before a click can predict click-through rate (CTR) for clients the model has never seen. It uses 30,000 pseudonymized content items from 32 clients (trailing 90-day metrics) and compares a gradient-boosting model with a simple median baseline under 5-fold validation grouped by client, with a random-row split as the comparison. Under the grouped split the model's mean absolute error was 0.00671 against 0.00525 for the baseline (27.9% higher), and the model was also behind the baseline under the random split, so no gain over a median guess was measured. A shuffled-target check showed no sign of a pipeline leak, so the result reads as weak signal in these features rather than a bug. Because of this, the paper turns the output into a low-confidence, decision-support review queue of 627 flagged items with reason codes, human-review rules, a no-go list and monitoring triggers, and it states clearly that nothing here should be automated.

1. Introduction and problem statement

Search-driven content teams have far more pages than editing hours. A common first question is which pages are under-performing for their situation, and a common signal for that is click-through rate (CTR), the share of impressions that become clicks. A model that predicts the CTR a page should get, from facts known before any click, could in principle point an editor to pages that fall well below that expectation.

Question. Can features known before a click predict CTR for new clients better than a simple baseline, and can the result support a practical, human-reviewed content action queue?

Why the validation design matters. A tool like this would be used on clients it was not trained on. If rows from one client appear in both training and test data, a model can learn client-specific habits and look better than it really is. This paper therefore evaluates on whole clients that were held out, and shows what changes against a random split.

Scope. This is an audit with a modest aim: report what was measured, say plainly where the evidence is weak, and describe how a team could use the output safely. It does not claim a production-ready model.

Label. CTR, stored in the file as a percentage (a value of 0.76 means 0.76%). It was divided by 100 so that the model works in fractions and "impressions times CTR gap" counts clicks.

Cleaning decisions.

  • No rows were removed: all 30,000 rows had a CTR and a client identifier.
  • An average position of 0 means "no data", so it was turned into a missing value rather than treated as rank zero.
  • Missing values follow content type (one type has almost no keyword data), so filling with zero would have injected a content-type signal. Instead, "has value" flags were added for six fields.
  • Measured: about 27% of items (7,994) have fewer than 100 impressions in the window. Their CTR is unstable and they are treated separately in the playbook.

Excluded from the features, on purpose. Click, session, engagement, scroll and AI-traffic columns (outcomes, not pre-click facts); impression columns (the denominator of CTR); the trend percentage and trend direction columns (the data documentation marks them as the source of the decline label, so they are never features); and the client and content identifiers (pseudonyms used only for grouping and for the queue). Everything shown here is public-safe: no client names, URLs or queries appear.

3. Methodology

Baseline. Predict the median CTR of the training clients for every item (a scikit-learn median DummyRegressor). It uses no features, so any useful model must beat it to show value.

Model. HistGradientBoostingRegressor (300 iterations, learning rate 0.05, default squared-error loss, fixed seed 42). It was chosen as a reasonable, explainable step up for tabular data that handles missing values; it was not tuned.

Features (26). Search volume, competition, cost per click, word count, character count, content age, days since last update, average position, six "has value" flags, and one-hot encodings of content type, main intent and competition level. All of these are facts about the item or its keyword context rather than outcomes of the click.

Validation. Five folds grouped by client (GroupKFold): every test fold contains only clients absent from its training folds. For comparison, the same model and baseline were also scored with an ordinary shuffled five-fold split. The main metric is mean absolute error (MAE) in CTR, averaged over folds; lower is better.

Leakage checks.

  • Outcome and denominator columns, trend columns and identifiers were excluded as listed above.
  • A shuffled-target check: when the CTR labels were randomly permuted, the model should not beat the baseline. It did not (section 4), which fits a pipeline without a hidden leak.
  • Random-split versus grouped-split comparison, to see how much a client-sharing split would flatter the model.

These checks are not exhaustive; they reduce, but do not remove, the chance of a hidden leak.

Assumptions. Each row is treated as one item in one fixed 90-day window; CTR is comparable across clients; no time ordering is used because the starter file has one snapshot per item.

Observed. Under the grouped split, the model's MAE was 0.00671 against 0.00525 for the baseline, which is 27.9% higher (worse). The model was also behind the baseline under the random split. In this sample, the features did not give a measured gain over predicting the median CTR.

Split effect. Moving from the random split to the grouped split raised the model's MAE by about 5% (0.00637 to 0.00671) and the baseline's by about 4% (0.00505 to 0.00525). That is a small, directional difference: sharing clients across train and test did not flatter the model much here, because there was little to flatter.

Client-to-client spread. The spread across folds is about 0.0044 under the grouped split, against about 0.0002 to 0.0003 under the random split. Which clients land in a test fold changes the score a great deal, so any single number should be read with that spread in mind.

Sanity check. With shuffled labels the model's grouped MAE was 0.00715, not below the baseline, as expected for a pipeline without a leak.

What the errors look like

CTR in this sample is heavy-tailed: most items sit near zero and a few sit far above. One plausible reason the median baseline wins on MAE is that the model was trained with a squared-error loss, which is pulled toward large values, while it was scored on absolute error. This was not tested here (see recommendation 5 in section 6). A concrete example of the failure: the third-ranked item in the review queue has an expected CTR of about 11.95% against an actual 0.05%, a prediction far above the median CTR of any content type in the sample (0.00% to 0.09%). Extreme predictions like this are exactly what a human reviewer should be able to dismiss.

Exploratory: CTR and content age

Median CTR was highest in the newest bucket (0.12%) and lowest in the 236 to 311 day bucket (0.03%), then partly recovered (0.06% to 0.07%) for older content. This is not a steady decline with age, so the data do not give clear support for any single refresh age. Age is also mixed up with topic, publish cohort and season.

5. Limitations and honest framing

Main finding: in this sample the model did not beat a median baseline on new clients. Everything in the playbook below is therefore a low-confidence aid for human review, not evidence that the flagged pages are failing.
  • One sample, one window. A single 30,000-item snapshot with trailing 90-day metrics. Other periods or other kinds of clients are not tested, and no time-aware validation was possible.
  • Large client differences. High spread across folds means results depend on which clients are held out. With 32 clients, the grouped test is coarse.
  • Heavy-tailed target and loss mismatch. The model's loss and the evaluation metric differ; a loss matched to MAE was not tried, so the model is not shown to be at its best.
  • No cause. The queue shows items below the model's expectation, not "bad content". Quality, intent shifts and seasonality are not in the features, and nothing here shows why a page's CTR is low.
  • Estimated clicks are directional. They assume an item could reach its expected CTR. A few items drive much of the total (the top two make up roughly 17% of estimated extra clicks among flagged items), and the expectations come from a model that did not beat the baseline.
  • Concentration. Nine of the ten highest-ranked queue items come from two clients, which could reflect those clients' data rather than general patterns.
  • Assumed numbers. The 100-impression cutoff, the 180-day age rule and the effort hours are my assumptions, not measurements.
  • Non-production. This is a plan and a queue produced in a notebook, not a deployed system.

6. Ranked recommendations: a content action playbook

Intended use. A ranked review queue that helps an editor decide which items to look at first. It is decision-support for planning refresh work, to be used only after the gate in recommendation 5 below is met.

Recommendations, in priority order

  1. Treat the queue as prompts for human review, not as findings. Because the model did not beat the baseline, every flag is a low-confidence reason to look at a page.
  2. Start with title and snippet reviews. Under assumed effort of 0.5 hours each, these gave the highest estimated extra clicks per hour (about 92, against about 24 for full refreshes). Directional only, since the hours are assumptions.
  3. Review aged flagged items for refresh next. Refresh candidates need an item both below expectation and older than 180 days; age is used as a prompt, not a cause (Figure 2 shows no clear age effect).
  4. Leave low-volume items alone or send them to a person. About 27% of items have fewer than 100 impressions, and most "feedly article" items are in this group, so their CTR is too unstable to act on.
  5. Re-validate before relying on it. Re-run grouped validation with a loss matched to MAE and on newer data. Use the queue only if the model beats the baseline on held-out clients.

Ranked actions and reason codes

Each item gets a model-expected CTR from a model that never saw its client. An item is flagged only when its actual CTR is below expectation by more than the model's own average error (the noise floor, 0.00671).

Reason codeMeaning
R1_BELOW_EXPECTEDActual CTR is below expectation by more than the noise floor.
R2_AGEDItem is older than 180 days (an assumed threshold).
R3_LOW_VOLUMEFewer than 100 impressions; CTR is unstable.
R4_WITHIN_NOISEGap is inside the noise floor; monitor only.

Actions: REFRESH_CONTENT (R1 and R2), REVIEW_TITLE_SNIPPET (R1 only), HOLD_LOW_VOLUME (R3, always for a person or left alone), MONITOR (otherwise). Items are ranked by estimated opportunity: impressions times the positive CTR gap.

Decay and refresh insight

Median CTR is lower for older content than for the newest content, but not steadily so (Figure 2). The 180-day refresh age is therefore a review prompt chosen for convenience, to be checked against fresh data before it is trusted.

Effort per item (3 hours for a refresh, 0.5 for a title review, 0.25 for a low-volume check) is an assumption, and estimated clicks assume items reach their expected CTR. Use the ratio to order work, not as a return-on-investment claim. A wasted refresh costs editor hours; a missed item costs clicks; this is why a person stays in the loop.

Human-review rules

  • A person reads every item in the top of the queue before any change is made.
  • Every low-volume item is reviewed by a person or left alone.
  • The reviewer sees the reason codes and the gap, and may override an action with a written reason.
  • A sample of MONITOR items is spot-checked to catch misses.

What should NOT be automated

  • Publishing, rewriting or deleting content straight from the queue.
  • Pruning pages based on a CTR gap alone.
  • Promises to clients such as "this refresh will lift CTR by X".
  • Decisions about very low-volume items, brand-new items with no history, or clients not represented in the sample.
  • Using the queue to rank or judge people or teams.
  • Reading the model's feature use as a cause of CTR.
  • Using the queue after a monitoring trigger fires, until it is re-validated.

Light monitoring and retrain triggers

  • Input drift: compare each key feature against the training sample with the population stability index (PSI). Above 0.25, look closely. In this sample, two random halves of clients already scored between 0.12 and 0.22, so client-to-client differences alone sit near that threshold. Calibrate it per client before relying on it.
  • Error check: if MAE on new data with known outcomes is more than 20% worse than the grouped-validation MAE, pause the queue.
  • Baseline check: if the model does not beat the baseline on held-out clients, do not use the queue (this is currently the case).
  • Queue sanity: if the share of flagged items moves by about 2x, investigate first.
  • Retrain: when any trigger fires, a new client segment is added, CTR measurement changes, or on a regular schedule such as quarterly (an assumption). Re-run grouped validation after retraining.

7. Reproducibility

  • Repository: github.com/arshiyanaaz411/flyrank-ml-internship
  • Notebook for every number in this paper: work/notebooks/w07_action_playbook.ipynb. It loads the starter file from the repository, runs the baseline, the model, the random and grouped validation, the shuffled-target check, the queue and the monitoring check. Open it in Google Colab and choose Run all.
  • Data: data/raw/content_refresh_anonymized.csv in the repository (30,000 rows, 44 columns).
  • Settings: model with 300 iterations and learning rate 0.05; random seed 42; five folds; impression cutoff 100; age threshold 180 days.
  • Outputs the notebook writes: the ranked queue file, a metrics file, and the figures. The queue file contains item-level rows and is regenerated by the notebook rather than stored in the repository.
